# Simulation time theory for a split party: PDES, distributed virtual environments, logical clocks and concurrency control

Reading notes. "The game" below means: host-authoritative co-op RPG, one persistent world, one typed action may cost seconds to days of game time, players split and reunite, narrated output is irrevocable in practice, regions advance lazily on arrival, no cap on players. "The proposal" means: clock per character; last-touched time per person, place and thing; time per region; rules touch / perceive / window (about two game days ahead of the slowest playing character).

Method note: sources were read in full text where a URL is marked (read); others are marked (abstract or search excerpt only). Direct quotation is avoided; statements are paraphrases. All "what this means for the game" material is in the Inferences blocks and is my reasoning, not something a source says.

A framing fact that colours everything below: the classical theory assumes many processors and an unreliable or slow network. The game has one authoritative host that knows every clock exactly. The only thing the host does not know is the timestamp of the next action each human will submit. So the game is a sequential simulator with human event sources that submit events out of timestamp order. Costs that the literature measures in messages and CPU show up in the game as human waiting time or as involuntary time skips.

## 1. Conservative parallel discrete event simulation (Chandy-Misra-Bryant, null messages, lookahead, LBTS, windows, YAWNS, HLA time management)

### Takeaway
Conservative schemes guarantee that nothing ever arrives in a participant's past, and they pay for that by making the participant who is ahead wait; how long depends entirely on lookahead (how far ahead each participant can promise not to affect others). The proposal's window rule is a moving time window of width two days above the global minimum clock; in HLA terms every playing character is both time-regulating and time-constrained and the slowest one withholds everyone else's time-advance grant.

### Cited Findings
- The synchronisation problem is the local causality constraint: each logical process (LP) must process its events in timestamp order; obeying it is sufficient for the parallel run to give the same result as a sequential run, provided same-timestamp events are ordered the same way. Conservative algorithms avoid violations by waiting until an event is safe; optimistic ones allow violations and recover by rollback. — [Fujimoto, course slides "Time Warp: Local Control" (read)](https://sigsim.acm.org/conf/mskr/Courseware/Fujimoto/Slides/FujimotoSlides-11-TimeWarpLocalControl.pdf)
- Chandy-Misra-Bryant assumptions: LPs exchange timestamped messages over a static topology; each link carries messages in timestamp order and delivers reliably in order. Therefore the timestamp of the last message on a link is a lower bound on the timestamp (LBTS) of anything that will later arrive on that link. An LP waits until every incoming queue is non-empty, then processes the smallest timestamp. This naive form deadlocks when a cycle of LPs each waits on the next. — [Fujimoto, slides "Deadlock Avoidance Using Null Messages" (read)](https://sigsim.acm.org/conf/mskr/Courseware/Fujimoto/Slides/FujimotoSlides-06-NullMessages.pdf)
- Null messages break the deadlock: after each event an LP sends each neighbour a content-free message whose timestamp is its current time plus its lookahead, a promise about the earliest thing it could send next. The algorithm depends on lookahead. In the airport example lookahead is the minimum flight time between airports. — [Fujimoto, null message slides (read)](https://sigsim.acm.org/conf/mskr/Courseware/Fujimoto/Slides/FujimotoSlides-06-NullMessages.pdf)
- Cost of poor lookahead, the time creep problem: with lookahead 0.5 and three LPs blocked at about time 5, five null messages (5.5, 6.0, 6.5, 7.0, 7.5) are needed before the one real event at time 7 can be processed. With zero lookahead around a cycle the null messages circulate forever without anyone advancing (livelock); zero-lookahead cycles are forbidden. Measured speedup on an 8x8 toroid falls sharply as the ratio of lookahead to mean timestamp increment falls from 0.9 to 0.1. The slides' summary line is that conservative algorithms live or die by lookahead. — [TU Munich simulation course, chapter 6 slides WS 2011/12, built on Fujimoto's material (read)](https://www.net.in.tum.de/pub/simulationstechnik/ws20112012/skript/ST_WS20112012_Ch6_ParallelSim.pdf)
- Synchronous (window) conservative algorithm: each round compute LBTS = min over LPs of (time of next event + lookahead); every LP may process all events with timestamp at or below LBTS; then a global barrier and repeat. Messages still in transit must be accounted for. An optimisation uses a distance matrix between LPs, on the principle that distant things cannot affect you for some time. — [TU Munich slides (read)](https://www.net.in.tum.de/pub/simulationstechnik/ws20112012/skript/ST_WS20112012_Ch6_ParallelSim.pdf)
- YAWNS (Nicol): with all LPs at time t, each LP i predicts d_i(t), the earliest time it could next affect another LP assuming it hears nothing new (conditional knowledge, in Chandy and Sherman's term). The window is [t, min_i d_i(t)). Everything inside the window is safe to run in parallel; then a global synchronisation. The paper notes that YAWNS builds very small windows, trading parallelism and frequent barriers for zero rollback overhead. — [Dickens, Nicol, Reynolds, Duva, "Analysis of Bounded Time Warp and Comparison with YAWNS", ACM TOMACS 6(4), 1996 (read)](https://www.cs.mcgill.ca/~carl/btwyawns.pdf)
- HLA offers two delivery orders. Receive order: low latency, no protection against temporal anomalies, not repeatable. Timestamp order (TSO): prevents anomalies, all federates see the same order, repeatable, higher latency. — [Fujimoto, slides "Time Management in the High Level Architecture" (read)](https://sigsim.acm.org/conf/mskr/Courseware/Fujimoto/Slides/FujimotoSlides-21-HLATimeManagement.pdf)
- HLA roles. A time-regulating federate may send TSO messages and can therefore hold back other federates' logical time. A time-constrained federate may receive TSO messages and has its advances limited by others. A federate may be both (the usual case for analytic simulation), only one (a pure source; a passive observer, the "stealth" viewer), or neither (training simulators in the DIS style). Flags can be enabled and disabled during a run. — [Fujimoto, HLA slides (read)](https://sigsim.acm.org/conf/mskr/Courseware/Fujimoto/Slides/FujimotoSlides-21-HLATimeManagement.pdf)
- HLA advance protocol. Logical time moves only when the federate asks. Time Advance Request (T): for time-stepped federates; the runtime delivers every TSO message stamped at or before T, then issues Time Advance Grant (T); the grant always equals the request. Next Message Request (T), called Next Event Request in some versions: for event-stepped federates; the runtime grants the earlier of T and the timestamp of the next incoming TSO message, delivering that message. Guarantee to the federate: once at logical time T it will never be handed a TSO message stamped before T. Obligation on the federate: with lookahead L it may not send a message stamped earlier than its time plus L; after a Next Message Request that promise is conditional on not receiving an earlier message. — [Fujimoto, HLA slides (read)](https://sigsim.acm.org/conf/mskr/Courseware/Fujimoto/Slides/FujimotoSlides-21-HLATimeManagement.pdf)
- Lookahead in HLA must be declared, non-negative; it may be raised at once but lowered only gradually as the federate advances (a promise already made cannot be withdrawn). Without lookahead, only events with exactly equal timestamps can be processed concurrently. — [Fujimoto, HLA slides (read)](https://sigsim.acm.org/conf/mskr/Courseware/Fujimoto/Slides/FujimotoSlides-21-HLATimeManagement.pdf)
- HLA mixes conservative and optimistic federates without their knowing about each other (synchronisation transparency): LBTS_i is the lower bound on messages that may still reach federate i; events below it are committed; the runtime hands only committed events to conservative federates, while optimistic ones may ask for uncommitted events and must accept retractions. — [Fujimoto, HLA slides (read)](https://sigsim.acm.org/conf/mskr/Courseware/Fujimoto/Slides/FujimotoSlides-21-HLATimeManagement.pdf)
- Zero lookahead was not supported in the baseline HLA and has consequences for repeatability. — [Fujimoto, "Zero Lookahead and Repeatability in the High Level Architecture" (search excerpt only)](https://sites.cc.gatech.edu/computing/pads/PAPERS/Zero_Lookahead_and_Repeatability.pdf)
- In a mixed system, Jefferson defines global virtual time as the minimum over optimistic objects' clocks, messages in transit, and conservative objects' clock plus lookahead. Conservative objects must stay at or below it and block rather than cross it. — [Jefferson, PDES course lecture 10, LLNL, 2014 (read)](https://gdo-pdes-course-2014.llnl.gov/attachments/20776356/23363701.pdf)

### Inferences
- Mapping of the window rule. "No playing character more than about two days ahead of the slowest" is the moving time window throttle (block at global minimum + w) with w fixed at two days. In HLA vocabulary each playing character is time-regulating and time-constrained; a long action is a time advance request; if the requested time exceeds minimum + w the grant is withheld. It is not a conservative safety rule in the CMB sense, because two days is not a lookahead: a character two days ahead can still be affected by a slower one. Safety in the proposal comes from touch and perceive; the window only bounds how bad the consequences get (size of an involuntary jump, depth of history that must be kept, amount of future already fixed by the leader).
- What a true conservative rule would look like in the game. Lookahead between two characters is the minimum game time for any influence to travel from one to the other: walking time between their places, or less if messages, magic or world-simulation effects are faster. A character i may safely advance to min over other playing characters j of (clock_j + d(j, i)). This is the airport example with travel time as flight time, and it is the distance-matrix optimisation. Under this rule nobody ever needs to be pulled forward on arrival, because the arriving character's travel time already covers the gap. Player experience: a lone traveller far from everyone almost never waits; two characters ten minutes apart are nearly in lockstep, and one of them cannot take an eight-hour rest until the other has also moved eight hours on. A co-located party has zero lookahead and must share a clock (the theory's "zero-lookahead cycle" is the party scene).
- Poor lookahead in the game does not cost null messages (the host knows all clocks, so LBTS is exact and free). It costs human waiting: the leader is blocked in real time until a slower human acts. That is the game's version of time creep: many tiny grants, each waiting on a person.
- Next Message Request is the right shape for long actions. "Walk two days" should be a request to advance to T that may be granted short (T' < T) when some other event reaches the character first: the walk is interrupted at T'. A time advance request is the uninterruptible form (the grant equals the request) and should be reserved for actions that cannot be interrupted. The HLA conditional-guarantee wording is exactly the semantics of an interruptible journey.
- YAWNS suggests computing the window instead of fixing it: each round, the host asks for every playing character the earliest game time at which that character could affect anyone else, and takes the minimum. Everything before that is free of conflict regardless of the order the humans submit in. The 1996 analysis warns that such safe windows are small when participants are densely coupled, so this buys most for well-separated players.
- HLA's roles answer the idle-player question. A player who is away should stop being time-regulating (dropped from the minimum), like the stealth observer. "Playing character" in the window rule already implies this. On return the character must re-enter at or above the current lower bound, because anything earlier is committed history; I did not verify HLA's exact late-join rule (see Gaps).
- No cap on players. A global minimum over all players makes the slowest of N throttle everyone, and the YAWNS-style window (a minimum over N predictions) shrinks as N grows. Neighbour-scoped constraints in the CMB style (only those who can reach you soon constrain you) scale; a single global window does not.
- Repeatability note for a host with goldens: timestamp order alone does not fix the order of equal-timestamp events. A deterministic tie-break (timestamp, sequence, actor id) is needed for repeatable replays, as Fujimoto's footnote and the HLA table imply.

### Gaps
- Bounded lag (Lubachevsky) and the original Moving Time Window (Sokol and others) were seen only as citations inside Dickens et al.; I did not read them.
- IEEE 1516 text itself was not read; the HLA material is from Fujimoto's slides. The zero-lookahead request variants (the "available" forms of the two advance requests) and the precise rule for a federate that enables time regulation late were not verified.
- Fujimoto's book "Parallel and Distributed Simulation Systems" (2000) was not accessible; the slides and the TU Munich deck derived from it stand in.

## 2. Optimistic simulation: Time Warp, virtual time, GVT, anti-messages, fossil collection, lazy cancellation, irrevocable operations

### Takeaway
Time Warp lets every process run ahead and repairs causality by rollback, but it never lets anything irreversible out until global virtual time (GVT) has passed it. Narration shown to a human is exactly Time Warp's irrevocable output, and because the game must show it immediately, the action that produces it has to be safe at the moment it runs; the proposal achieves this by moving the late actor forward instead of rolling the early one back.

### Cited Findings
- Virtual time (Jefferson, 1985) imposes one totally ordered time coordinate on a distributed computation. Each process has a local virtual clock; messages carry virtual send and receive times; the rules are Lamport's clock conditions. Jefferson describes Time Warp as the inverse of Lamport's algorithm: Lamport assigns clock values to an execution that already happened; Time Warp is given the timestamps and must produce an execution consistent with them. He argues that inside virtual time one can reason with ordinary Newtonian intuition and does not need the relativistic care that real-time distributed reasoning needs. — [Jefferson, "Virtual Time", ACM TOPLAS 7(3), July 1985 (read)](https://gdo-pdes-course-2014.llnl.gov/attachments/20776356/20907222.pdf)
- Mechanism. Each LP processes whatever it has, in timestamp order, but keeps processed events, saved states and an output queue holding a negative copy (anti-message) of everything it sent. A straggler (message stamped in the LP's past) makes it restore the state before that time, send the anti-messages for everything sent after that time, and re-execute. An anti-message meeting its positive twin annihilates it; if the twin was already processed, the receiver rolls back too (secondary, cascaded rollback). — [Fujimoto, Time Warp slides (read)](https://sigsim.acm.org/conf/mskr/Courseware/Fujimoto/Slides/FujimotoSlides-11-TimeWarpLocalControl.pdf)
- Jefferson's 1985 paper names the hard cases explicitly: messages may have asked for output or other irreversible action (his examples: dispensing money, launching a missile), and all of it must be effectively unsent. — [Jefferson 1985 (read)](https://gdo-pdes-course-2014.llnl.gov/attachments/20776356/20907222.pdf)
- GVT is the minimum timestamp of any unprocessed or partly processed message or anti-message (Jefferson's later definition: min of local clocks and in-transit message times). It never decreases and bounds every future rollback from below. Jefferson calls it a moving commitment horizon: anything earlier can be committed for good. — [Jefferson 1985 (read)](https://gdo-pdes-course-2014.llnl.gov/attachments/20776356/20907222.pdf); [Fujimoto, Time Warp slides (read)](https://sigsim.acm.org/conf/mskr/Courseware/Fujimoto/Slides/FujimotoSlides-11-TimeWarpLocalControl.pdf)
- Output rule. A command to an output device or any external agent must not be physically performed when issued, because the sender may roll back. It is performed only once GVT exceeds the command's virtual receive time, and outputs are released in timestamp order. Errors are treated the same way: an error is reported only when the erroring state is older than GVT, since before that the process may roll back and "un-err". — [Jefferson 1985, sections 4.3.3 and 4.3.4 (read)](https://gdo-pdes-course-2014.llnl.gov/attachments/20776356/20907222.pdf)
- Fossil collection: saved states and messages older than GVT (keeping one state) are reclaimed. Input from outside is buffered so it can be "un-input" on rollback, and the buffers are freed when GVT passes. Jefferson's 2014 list of what an optimistic system must cope with includes truly irreversible operations (I/O, freeing storage, launching a missile). — [Jefferson, LLNL course lecture 10, 2014 (read)](https://gdo-pdes-course-2014.llnl.gov/attachments/20776356/23363701.pdf)
- An estimate of GVT must err low: too high would commit events that can still be rolled back, which Jefferson calls a disaster; too low merely delays commitment. — [Jefferson, LLNL lecture 10, 2014 (read)](https://gdo-pdes-course-2014.llnl.gov/attachments/20776356/23363701.pdf)
- Cancellation variants. Aggressive: on rollback, cancel at once everything sent after the rollback time. Lazy: cancel nothing at rollback; on re-execution compare what is generated now with what was sent before; identical messages stand, new ones are sent, only the ones not regenerated are cancelled. Lazy cancellation wins when the straggler touched a part of the state that the already-sent messages did not depend on. Risk-free: treat outgoing messages as output and hold them until GVT passes; no anti-messages, no secondary rollbacks, only local ones. — [Jefferson, LLNL lecture 10, 2014 (read)](https://gdo-pdes-course-2014.llnl.gov/attachments/20776356/23363701.pdf)
- Jefferson's cost argument for rollback is a conjecture of temporal locality: most messages arrive in the receiver's future, and stragglers land in the recent past, so few events are undone. He says it is application dependent and only checkable empirically. — [Jefferson 1985 (read)](https://gdo-pdes-course-2014.llnl.gov/attachments/20776356/20907222.pdf)
- A process with nothing to do has its clock set to plus infinity so that it does not hold GVT back; a later message revives it. — [The Morning Paper summary of Jefferson 1985 (read)](https://blog.acolyer.org/2015/08/20/virtual-time/)

### Inferences
- Correspondence. Narration read by a human = irrevocable output. Time Warp's answer is to buffer it until GVT passes. The game cannot buffer by default (the player is waiting for the reply), so it must do one of two things at the moment of narration: (a) prove the narrated content is already below the lower bound of anything that can still arrive (conservative safety), or (b) take a stamp on everything the narration relied on, so that any later, earlier-timestamped actor is moved forward to after it. The proposal's touch rule is (b): where Time Warp rolls the receiver back, the game rolls the sender forward. This is legitimate because a human player has no pending earlier commitments that the move would violate; what it costs is that player's unspent time.
- What "GVT" is in the game: the minimum clock over playing characters. Everything before it is closed history that nobody can ever act in. Engineering consequences: versions of object and region state older than that are fossils (keep one); the window rule bounds the depth of version history to about two days; a player who goes idle should be treated as clock = infinity so the minimum is not pinned.
- What can still be optimistic. Time Warp separates internal state (freely rolled back) from output (held). In the game, any world-simulation state that has not been told to anyone is internal. The engine can advance regions speculatively and throw the result away. Lazy regional advance is the degenerate, zero-waste case of this.
- Lazy cancellation gives a more permissive admission test than a coarse region stamp. If a slower character acts at an earlier time in a region that has already been advanced past that time, re-run the region's engine simulation from the earlier time and compare the facts that were already narrated (the facts the engine put into narrator prompts are the narration's read set). If none changes, the earlier-dated act can stand without moving the actor forward. If any narrated fact would change, fall back to touch (move the actor to after the narration). This keeps irrevocability intact and avoids needless time skips, at the price of tracking read sets and of re-simulating engine state (not model calls).
- "Delay the bad news" is the only other tool the theory offers: outputs with heavy consequences for other players could be released at commit time rather than at once. In a narrative game that is rarely acceptable for the acting player, but it is plausible for what other players are told about that act (see perceive, sections 4 and 5).
- Temporal locality is the empirical question for the game too: how often do players act on things another player has already been told about at a later time? If rare, promotion-on-touch is cheap and the window can be generous; if common (hub town, shared quest giver), jumps will be frequent and the hub effectively forces a shared clock.

### Gaps
- I did not find a source on Time Warp systems with a human in the loop consuming output interactively; the HLA treatment (pass only committed events to non-optimistic federates) is the nearest.
- Reverse computation and other alternatives to state saving were not researched; they do not help with narrated output in any case.

## 3. Hybrid and adaptive schemes (bounded optimism, moving time windows, Bounded Time Warp, Breathing Time Buckets / Breathing Time Warp, risk-free optimism)

### Takeaway
Each hybrid limits one specific cost of pure optimism: windows cap how far anyone runs ahead (so rollbacks are short), risk-free variants forbid wrong information from leaving a process (so rollbacks never spread), and breathing schemes let the window size be set by the events themselves. No good theory exists for choosing a fixed window width, which is a direct caution about "two days".

### Cited Findings
- Throttling is any mechanism that reduces excess optimism; the costs of excess optimism are extra storage, the local rollback work, and other processes' handling of messages that should never have been sent. — [Jefferson, LLNL lecture 10, 2014 (read)](https://gdo-pdes-course-2014.llnl.gov/attachments/20776356/23363701.pdf)
- Moving Time Window: every object blocks on reaching GVT + w; when all have reached it GVT is recomputed and the window moves. The width can adapt, or be counted in events instead of time units. Jefferson states that how to choose and adapt w is handled empirically and that he finds the absence of a theory unsatisfactory. — [Jefferson, LLNL lecture 10, 2014 (read)](https://gdo-pdes-course-2014.llnl.gov/attachments/20776356/23363701.pdf)
- Bounded Time Warp: optimistic execution inside a window, with a global synchronisation at the window's upper edge; no separate GVT algorithm is needed and cascading rollbacks are contained in the window. Analysis for a heavily loaded queueing network: the best BTW window is much larger than the YAWNS window, yet an LP processes only one or two events in it on average; the fraction of useful work falls linearly as the window widens past a point; the number of rollbacks and the events redone per rollback both grow linearly with window width. — [Dickens, Nicol, Reynolds, Duva, ACM TOMACS 1996 (read)](https://www.cs.mcgill.ca/~carl/btwyawns.pdf)
- Breathing Time Buckets (Steinman, SPEEDES, about 1991-92) combines the conservative time-bucket idea with Time Warp's optimism, with a first-principles performance model. — [NASA NTRS record for Steinman, "SPEEDES: a multiple-synchronization environment for parallel discrete-event simulation", 1992 (abstract read)](https://ntrs.nasa.gov/citations/19930070828)
- Breathing Time Buckets sends only messages known to be valid, so it amounts to risk-free Time Warp; it can be too conservative, processing too few events per cycle; Breathing Time Warp mixes the two phases. — [SPEEDES patent text, US 5,794,005 or US 6,324,495 (search excerpt only; which of the two patents carried the passage was not checked)](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/5794005)
- Breathing Time Warp limits optimistic execution by confining rollback to events inside an event horizon (Steinman 1993). — [Delaney, Ward, McLoone, "On Consistency and Network Latency in Distributed Interactive Applications: A Survey, Part I", Presence 15(2), 2006 (read)](https://perso.lisn.upsaclay.fr/mbl/ENS/CSCW/2022/papers/Delaney2006.pdf)
- Risk-free execution: primary rollbacks still happen, secondary and further ones do not. — [Jefferson, LLNL lecture 10, 2014 (read)](https://gdo-pdes-course-2014.llnl.gov/attachments/20776356/23363701.pdf)

### Inferences
- The proposal as a hybrid. Touch + perceive + window is closest to a risk-free, windowed scheme with forward promotion in place of rollback: nothing a character does is exposed to others in a way that could later be withdrawn, and a global window caps divergence. What the window caps is different, though. In Bounded Time Warp it caps rollback length. In the game there is no rollback, so it caps pre-emption: how much of the shared future the leader can fix (by being told about it) before the others have had a chance to act in it. That is the quantity to tune, and it argues for thinking of the window per shared object or per region rather than as one global number: a leader alone in the wilderness pre-empts nothing.
- The event-horizon idea transfers well. Let each player act freely while their actions are private (nothing that another playing character could observe or touch within the window). The first action that emits something others could meet (entering an occupied or stamped region, touching a shared person, sending a message) is that player's horizon; the minimum of the horizons is how far everyone can go without coordination. The bucket "breathes": long when players are apart and self-contained, short when they converge. Player experience: no waiting at all while apart, and a natural sync point exactly when stories are about to cross.
- Jefferson's complaint about w applies. A fixed two days has no theoretical basis; the defensible candidates are (a) distance-derived (section 1), (b) horizon-derived (above), or (c) a pure experience budget ("nobody should ever be skipped more than N hours without consent"), in which case it should be named as such and tuned by playtest.
- The 1996 result that useful windows hold only one or two events per participant suggests not over-engineering: in a turn-based game a "window" is about one long action per player anyway.

### Gaps
- Steinman's own definition of the event horizon (I believe: the earliest timestamp among events newly generated in the current cycle, with everything before it committable) is from background knowledge; the primary papers were not retrieved.
- Adaptive-optimism literature after the 1990s (for example adaptive throttles in modern simulators) was not surveyed.

## 4. Logical clocks, vector clocks, causal ordering: is "last-touched time per object plus clock per actor" a known scheme?

### Takeaway
Yes. It is Lamport's receive rule with objects treated as passive processes (take the maximum, then advance), and equally the per-item timestamps of timestamp-ordering concurrency control with "retry at a later timestamp" done before execution. Its guarantee is one-way (cause before effect implies earlier timestamp); its known weaknesses are ratcheting (one far-ahead clock drags everything that meets it), blindness to out-of-band communication, and the need to stamp reads as well as writes.

### Cited Findings
- Lamport (1978): the clock condition requires that if event a can causally affect event b then C(a) < C(b). It is achieved by two rules: a process advances its clock between events; a message carries the sender's clock and the receiver sets its clock to at least its own value and greater than the message's. Ties are broken by an arbitrary fixed order of processes to obtain a total order. The converse does not hold: a smaller timestamp does not imply causation. — [Lamport, "Time, Clocks, and the Ordering of Events in a Distributed System", CACM 21(7), 1978 (PDF retrieved; rule headings confirmed, wording paraphrased)](https://lamport.azurewebsites.net/pubs/time-clocks.pdf)
- Lamport's paper also discusses anomalous behaviour: orderings that people perceive through channels outside the system are invisible to logical clocks, and avoiding that requires physical clocks kept within a bound. — [Lamport 1978 (section heading confirmed in retrieved text; content from background knowledge)](https://lamport.azurewebsites.net/pubs/time-clocks.pdf)
- Scalar clocks lose causal information (different processes can produce equal timestamps; causality cannot be read back from the numbers). Vector clocks (Mattern 1988, Fidge 1988) keep one entry per process and recover it. Roberts and Sharkey (1997) proposed "sufficient" causal ordering for virtual environments, where the application chooses which events need causal ordering and transient states superseded by an absolute later event may be skipped. — [Delaney et al. 2006 survey (read)](https://perso.lisn.upsaclay.fr/mbl/ENS/CSCW/2022/papers/Delaney2006.pdf)
- Vector clocks need space proportional to the number of nodes, which Kulkarni et al. call prohibitive; logical clocks find one consistent snapshot where vector clocks find all. — [Kulkarni, Demirbas, Madeppa, Avva, Leone, "Logical Physical Clocks and Consistent Snapshots in Globally Distributed Databases", 2014 (read)](https://cse.buffalo.edu/tech-reports/2014-04.pdf)
- Hybrid logical clocks: goal is a timestamp l with (1) cause before effect implies smaller l, (2) constant space, (3) bounded size, (4) l close to physical time. The naive rule, l := max(l + 1, l of message + 1, physical time), satisfies (1) and (2) but lets l drift without bound away from physical time, because one variable is doing two jobs (max physical time heard, and event counting). The fix splits it into l (max physical time heard, no +1) and a counter c for ties; then (l, c) respects causality and l minus physical time is bounded. — [Kulkarni et al. 2014 (read)](https://cse.buffalo.edu/tech-reports/2014-04.pdf)
- Reed's pseudotime underlies multiversion timestamp ordering in databases. With multiple versions a read stamped earlier than the current version can be served from an older version; a write stamped earlier than the current version usually forces abort and restart with a later timestamp. — [Jefferson 1985, related work and database section (read)](https://gdo-pdes-course-2014.llnl.gov/attachments/20776356/20907222.pdf)

### Inferences
- Exact correspondence. Treat every person, place and thing as a passive Lamport process. An act is a message exchange between the actor and each object touched: the actor first takes max(own clock, object time) (Lamport's receive rule; the touch rule), performs the act with its duration, and the object's time becomes the actor's new clock. Perceive is a multiversion read at the reader's timestamp. So the proposal is Lamport clocks over a bipartite graph of actors and objects, read through the lens of multiversion timestamp ordering. It is not a hybrid logical clock; but game calendar time plays the part that physical time plays for HLC, and the HLC paper's analysis of the naive max rule is the relevant warning.
- Guaranteed property: for any chain of touches from event a to event b, time(a) is at or before time(b). World history sorted by game time is therefore a legal causal history, and Jefferson's point applies: once everything is stamped on one time axis, players and designers can reason about before and after with everyday intuition.
- Failure mode 1, ratcheting and time attractors. Clocks only move by max. Any object touched by the leader carries the leader's time; everyone who later touches it jumps. Popular objects (the innkeeper, the town gate, a quest giver) become attractors that pull every visitor to the maximum clock that has ever visited. This is the scalar-clock behaviour that the HLC paper shows drifting without bound; the window rule is the game's bound on that drift. The useful side: touching a common object is also the mechanism by which a split party resynchronises.
- Failure mode 2, the skipped interval. In a simulator, a process whose clock jumps had no events in the skipped interval by construction. A player character does have a life in that interval (hunger, spell durations, deadlines, what the character "was doing"). The engine must apply elapsed-time effects for the skipped span and the narrator must account for it; the player experiences an unrequested time skip. This is the main human cost of the scheme and has no analogue in the clock literature.
- Failure mode 3, reads must stamp. Timestamp ordering needs a read time as well as a write time per item: a write dated before somebody's later read of the same item invalidates that read. For the game: if the leader was narrated the statue standing on day 3, a slower character must not smash it on day 1. So being narrated a thing has to count as touching it for the purpose of last-touched time. If "last-touched" records only acts, the scheme is unsound against already narrated text.
- Failure mode 4, absence and phantoms. A narration such as "the square is empty" or "no news from the north" reads a predicate, not an object. Per-object stamps cannot protect it; a slower character can later create a new fact inside it. The region time is the coarse stamp that covers this (entering a region whose time is ahead moves you forward). For remote predicates (news, rumours) the narrator should not assert absence about places whose time is behind the listener's clock.
- Failure mode 5, out-of-band knowledge. Players talk to each other outside the game. The leader can tell a slower player what happens on day 3. No clock scheme sees this (Lamport's anomalous behaviour). The only mitigation the theory offers is bounding clock skew, which is one more job the window does.
- Vector clocks are not needed. Their benefit is detecting that two events are causally unrelated, which would let the engine reorder them freely; the cost grows with the number of players, which is unbounded here. A scalar game time with a tie-break counter and actor id gives the total order Lamport describes and suffices for a host that executes everything itself.

### Gaps
- I did not find a paper that names "Lamport clocks on data objects in a game world" as such; the identification with timestamp ordering is my reading of standard material.
- The standard textbook account of basic timestamp ordering with separate read and write timestamps per item (Bernstein and Goodman) was not retrieved; it is cited here only through Jefferson's related-work discussion.

## 5. Temporal consistency in distributed virtual environments (local lag, timewarp, dead reckoning, bucket synchronisation, trailing state, consistency-throughput, interest management, local perception filters)

### Takeaway
The virtual-environment literature already accepts that users can see one consistent world at different times ("delayed consistency"), and local perception filters make that systematic: each user is the origin of their own time frame, others are seen at an offset, and the offset must shrink to zero as users approach, which requires a speed limit on anything that carries influence. That is the published idea nearest to per-character clocks, and its central constraint (time difference bounded by distance over maximum speed) is the same as conservative lookahead.

### Cited Findings
- Taxonomy (Delaney et al. 2006): time-management techniques either manage consistency (total order, causal order, clock synchronisation) or hide its absence (delayed consistency, time warp, local perception filtering). Discrete applications need only correct order (logical clocks suffice); continuous ones also need events to appear at the right absolute time. — [Delaney et al. 2006 (read)](https://perso.lisn.upsaclay.fr/mbl/ENS/CSCW/2022/papers/Delaney2006.pdf)
- Lockstep: nobody advances the simulation clock until all have acknowledged the current step; consistent, but response is at the mercy of the slowest acknowledgement. — [Delaney et al. 2006 (read)](https://perso.lisn.upsaclay.fr/mbl/ENS/CSCW/2022/papers/Delaney2006.pdf)
- Bucket synchronisation (MiMaze; Gautier and Diot 1998-99): synchronised time is cut into fixed buckets; events are assigned to buckets and executed after a fixed delay long enough for remote events to arrive. MiMaze's variant does not detect or repair late events; a missing event is dead reckoned from the previous bucket and only the latest event per member per bucket is used. — [Delaney et al. 2006 (read)](https://perso.lisn.upsaclay.fr/mbl/ENS/CSCW/2022/papers/Delaney2006.pdf); [Cronin, Kurc, Filstrup, Jamin, "An Efficient Synchronization Mechanism for Mirrored Game Architectures (Extended Version)", 2003 (read)](https://www.comp.nus.edu.sg/~bleong/hydra/related/cronin03efficient.pdf)
- Local lag (Mauve and colleagues): the local user's own operations are delayed before execution so that they can reach other sites in time; this lowers responsiveness to reduce short-term inconsistency. An "event prologue" can fill the gap between the user's action and its effect so that the delay feels natural. Suggested bounds: lag at least the largest average network delay between users; acceptable response from about 100 ms for dragging to about 400 ms for clicking; finding the optimum was left open. Local lag reduces but cannot eliminate short-term inconsistencies, so a timewarp (rollback and replay) repair is added, and compared with dead reckoning. — [Delaney et al. 2006 (read)](https://perso.lisn.upsaclay.fr/mbl/ENS/CSCW/2022/papers/Delaney2006.pdf); [Mauve, Vogel, Hilt, Effelsberg, "Local-lag and Timewarp: Providing Consistency for Replicated Continuous Applications", IEEE Trans. Multimedia 6(1), 2004 (abstract only; the PDF text could not be extracted)](https://madoc.bib.uni-mannheim.de/5925/)
- Delayed global consistency (Qin 2002, whiteboards): users need not hold the same state at the same moment; they see the same consistent world shifted in time, with the shift fixed at design time. — [Delaney et al. 2006 (read)](https://perso.lisn.upsaclay.fr/mbl/ENS/CSCW/2022/papers/Delaney2006.pdf)
- Local perception filters, as summarised by Delaney et al.: Sharkey, Ryan and Roberts (1998) applied ideas from relativity. Each user sits at the origin of their own space-time frame and every other user is at a relative space-time position. A critical velocity, the maximum speed at which information can pass between two users, delimits causal surfaces and volumes (the regions in which past events can affect the present and the present can affect the future). On these they define a "3½-D" perception filter: a continuously differentiable delay contour laid over the environment. The local user sees each remote user acting smoothly in that remote user's surroundings, delayed by the latency between them; as two users approach and begin to interact, the delay between them is interpolated to zero. The warping can distort apparent physics (objects seem stiff; "distributed stiffness"), and the authors present it as a new consistent physics in which users can make sense of delay, at the price of limits on speed. — [Delaney et al. 2006 (read)](https://perso.lisn.upsaclay.fr/mbl/ENS/CSCW/2022/papers/Delaney2006.pdf)
- Local perception filters, as taught from Smed and Hakonen's textbook: entities are active (players; unpredictable; shown from their updates, hence late) or passive (balls, rocks, projectiles; predictable; can be shown at any chosen time). The rendered time of a passive entity depends on where it is: near the local player it is shown at the current time, near a remote player at that player's delayed time, in between at an intermediate time. In two-player Pong with latency d, each player sees a different picture of the same game: the ball speeds up as it nears the local paddle and slows as it nears the remote paddle. The filter is a time coordinate attached to every point of space, zero at the local player and minus d at the remote one. Design rules: interact in real time with nearby things; see remote interactions happen smoothly even though late; keep distortion unnoticeable. Causality is preserved but the view is not the true state, and it is not dead reckoning. Delays can also be introduced on purpose, for example bullet time. — [Lecture slides "9.4 Local Perception Filters" after Smed and Hakonen (read via page text)](https://api.sambuz.com/doc/9-4-local-perception-filters-9-4-local-perception-filters-document-1054126)
- Original paper: Sharkey, Ryan, Roberts, "A local perception filter for distributed virtual environments", VRAIS 1998; companion: Ryan and Sharkey, "Distortion in distributed virtual environments", LNCS 1434, 1998. Extension to deliberate time manipulation: Smed, Niinisalo, Hakonen, "Realizing the bullet time effect in multiplayer games with local perception filters", Computer Networks 49(1), 2005. — [University of Reading repository record (bibliographic only; page blocked automated access)](https://centaur.reading.ac.uk/19079/); [DBLP record for Smed et al. 2005](https://dblp.uni-trier.de/rec/journals/cn/SmedNH05.html)
- Trailing state synchronisation (Cronin et al. 2002-04): keep several complete copies of the game state, each executing the same commands after a different delay. Only the leading copy is shown. Trailing copies, having waited longer, see fewer misordered commands; when a trailing copy's result differs, the leading state is overwritten from it and the later commands are replayed. Compared with Time Warp it avoids a snapshot per command (a Quake context was about 1 MB with a command every 30 ms per client). The paper admits what the player sees: position jumps, and now and then something drastic such as coming back to life after being shown dead; it suggests slightly delaying the announcement of a death in case of rollback. It also classes commands as weakly consistent (movement; approximate agreement suffices) and strictly consistent (weapon fire; exact time and place must agree, and they tighten the requirement on nearby movement). — [Cronin et al., extended version 2003 (read)](https://www.comp.nus.edu.sg/~bleong/hydra/related/cronin03efficient.pdf)
- Dead reckoning: remote entities are extrapolated from a model between updates; an update is sent when the true state departs from the model by a threshold; a larger threshold trades spatial error against fewer, later corrections. — [Roberts, Marshall, McLoone, Delaney, Ward, "Exploring the use of local consistency measures as thresholds for dead reckoning update packet generation", about 2005 (read)](https://mural.maynoothuniversity.ie/id/eprint/1308/1/TWFinal_DSRT05_Draft2.pdf)
- Consistency-throughput trade-off (Singhal and Zyda 1999): shared state cannot both change often and be guaranteed identical at all hosts at once; a world is either mostly static and identical everywhere, or dynamic without absolute consistency. — [J. Huang, networked games course notes reproducing Singhal and Zyda (secondary; the book was not retrieved)](https://web.eecs.utk.edu/~huangj/netgames/notes/dynamicstates.html)
- Consistency versus responsiveness, and interest management: an architecture cannot be both highly consistent and highly responsive. Interest management lets each node declare the subset of information it cares about. The aura (area of interest) is the subspace in which interaction happens; when two auras intersect the parties become aware of each other. Splitting aura into focus (what the observer perceives) and nimbus (how perceivable the observed is) allows one-way awareness. Implementations: exact formulae, fixed cells, or bounding extents. — [Smed, Kaukoranta, Hakonen, "Aspects of Networking in Multiplayer Computer Games", 2002 (read)](https://sites.cs.ucsb.edu/~almeroth/classes/W10.290F/papers/net-aspects-02.pdf)
- Lag compensation (Bernier, Valve, 2001; explained by Gambetta): each player sees themselves in the present and everyone else in the past. When a shot arrives the server rebuilds the world as the shooter saw it and judges the hit there. Accepted side effect: a target can be hit shortly after reaching cover from their own point of view; the author calls this somewhat unfair but better than the alternative. — [Gambetta, "Fast-Paced Multiplayer (Part IV): Lag Compensation" (read)](https://gabrielgambetta.com/lag-compensation.html); [Valve Developer Community, Bernier's paper (page blocked; search excerpt only)](https://developer.valvesoftware.com/wiki/Latency_Compensating_Methods_in_Client/Server_In-game_Protocol_Design_and_Optimization)

### Inferences
- Local perception filters applied to the game. Give each character its own "now". The world, seen from that character, has a time attached to every place: the character's own clock where they stand, and for a place occupied by another character, a time that depends on that character's clock. The filter's two laws carry over directly. (1) Seeing at a distance is allowed at an offset: what you learn about a far place is dated, and smoothly so. (2) Interaction requires zero offset: before two characters can act on each other or on the same thing, their times must be brought together. The proposal's perceive rule is law 1; touch is a blunt form of law 2 (an instantaneous jump instead of a smooth contour).
- The filter's speed limit is the missing piece in the proposal. In the original, the delay contour's slope is limited by the maximum speed of anything that carries influence, so an object travelling from one user to the other passes continuously from one time frame to the other. In the game, travel takes game time: if the clock difference between two characters never exceeds the travel time between them, the slower one's journey toward the faster one absorbs the difference and arrival needs no artificial jump. A flat two-day window ignores distance: it is too loose for two characters an hour apart (a jump of up to two days on meeting) and needlessly tight for two characters a week apart. A distance-scaled window is the perception-filter version and coincides with conservative lookahead (section 1).
- One asymmetry the filter does not have. With network lag both users see each other in the past, symmetrically. In the game the offsets are real differences in lived game time. The slower character can be shown the faster one's recorded past exactly (it is known). The faster character cannot be shown the slower one at the faster clock, because the slower human has not played that time yet. So mutual knowledge is always as of the lower of the two clocks: current for the slower player, stale for the faster ("last you heard, two days ago, she was in the village"). This is the honest form of dead reckoning for a narrator: state the last known fact and its age, never extrapolate as fact, because the correction would be a retcon.
- Meeting when the faster character goes to the slower one is the hard direction. The faster character's arrival is a message into the slower one's future, which is legal. But narrating the arrival needs the state of the slower character's place at the arrival time, which depends on moves the slower human has not made. Only three resolutions exist, and the theory names each: block the arriving player until the other catches up (conservative grant withheld), skip the resident player forward to the arrival time (promotion; what touch plus lazy regional advance does by default; "two days pass quietly, then he walks in"), or let the arrival stand as a pending event that the resident meets when their clock gets there while the arriving player's own narration is held (local lag with an event prologue: narrate the departure and the road now, hold the arrival scene). The choice is a fairness decision about who yields, not a correctness one. The window caps the worst case of whichever is chosen.
- Active versus passive entities is a useful classification for the world simulation. Anything that is a deterministic function of time and seed and that no player has influenced (weather, tides, a patrol on a fixed route, an untouched faction schedule) is passive: it can be evaluated at any character's clock, for free, with no stamps. Anything a human has influenced or been told about is active from that point and is pinned to stamps. Keeping as much of the world passive as possible is what makes per-character clocks cheap.
- Cronin's command classes suggest stratifying game state by required consistency: private state (own inventory, private thoughts; no coordination), ambient state (passive, above), and shared mutable state (who is alive, what is locked, who holds what; strict timestamp order with stamps on reads). Only the last class needs the three rules.
- Bucket synchronisation is the simultaneous-turn (play-by-mail) model: fix a bucket of game time, collect everyone's intent, resolve together. It guarantees consistency and makes the slowest human the pace of the whole table. The game's range of action durations (seconds to days) is the argument against one fixed bucket; a bucket sized by the next cross-player event (section 3) is the adaptive form.
- Interest management answers "who must be mutually consistent". Regions are cells; a character's consistency group is the set of characters and stamped objects whose areas of interest overlap its own, where area of interest should mean reachable within the window, not merely the same cell. Constraints should be evaluated inside that group. With unbounded players this is what keeps one distant slow player from throttling strangers. Focus and nimbus map onto perceive: a scout may see without being seen, so awareness need not be symmetric.
- The Singhal-Zyda trade-off, restated for the game: a world that every player sees identically at the same game time must either change rarely or make players wait for each other. Per-character clocks choose "dynamic, not simultaneously identical", which is the delayed-consistency position: one consistent history, viewed at different times.
- Lag compensation is a precedent for accepting a small, bounded unfairness to the party who is "ahead" in exchange for honouring what the other party was shown. The game's analogue of "what the shooter saw" is "what the player was told": the engine should always honour narrated text and push the inconsistency onto whoever has not yet been told anything.

### Gaps
- The full text of Sharkey, Ryan and Roberts (1998) and of Smed, Niinisalo and Hakonen (2005) could not be retrieved (repository blocked, publisher paywall). Details I recall but could not verify here: the exact contour functions; the statement that players must keep a minimum separation proportional to latency times maximum object speed ("critical proximity"); and that bullet time is produced by enlarging one player's temporal offset and reshaping the contours around them.
- Mauve et al. 2004 was retrieved but its PDF text layer was unreadable; local-lag details are from the Delaney survey and the abstract.
- Singhal and Zyda's book and Steed and Oliveira's "Networked Graphics" were not accessible; the trade-off statement is second-hand.
- Bernier's paper itself returned an access error; its content is represented by Gambetta's explanation and a search excerpt.

## 6. Rollback netcode (GGPO style) and its limits

### Takeaway
Rollback netcode works because a fighting game's state is tiny, fully serialisable, deterministic and cheap enough to re-simulate many frames inside one frame, and because the only output is a picture that is replaced sixty times a second. Each of those conditions fails for a narrated game: transitions involve model calls, the output is prose a person has read, and the "frame" being rolled back would be a whole human turn.

### Cited Findings
- GGPO requirements: the simulation must be fully deterministic; the game state must be fully encapsulated and serialisable; the engine must be able to run a simulation frame without rendering it. The library asks the game to save state, load state and advance a frame, and during a rollback it calls the advance callback many times in a row. Rendering and audio are outside the saved state. — [GGPO Developer Guide, project repository (read)](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md)
- How it hides latency: local input is applied after a small frame delay; when remote input has not arrived the library predicts it and runs ahead speculatively; when the real input differs, it reloads the earlier state and re-simulates. When the prediction limit is reached the game must stop advancing. — [GGPO Developer Guide (read)](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md)
- Side effects: sounds and visual effects triggered during a rollback must be deferred until the rollback finishes, and a short effect can be swallowed entirely by a rollback; remedies are more frame delay or delaying the effect in the renderer. Longer rollbacks are more noticeable. Suggested delays: most intermediate fighting-game players notice more than one frame; board or puzzle games tolerate four or five. — [GGPO Developer Guide (read)](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md)
- Fighting games need low and steady latency because play depends on timing and practised execution, and rollback is favoured for how well it hides poor connections. — [Infil, "Netcode" explainer, 16 Oct 2019 (introduction read; the body of the article was not returned)](https://words.infil.net/w02-netcode.html)
- The same pattern at larger scale already strains: Time Warp for a first-person shooter needs a megabyte-scale context saved per command, and incremental snapshots require an engine built around undo. Visible artefacts include players returning to life. — [Cronin et al. 2003 (read)](https://www.comp.nus.edu.sg/~bleong/hydra/related/cronin03efficient.pdf)

### Inferences
- Why it cannot carry narrated state. (1) Re-simulation cost: a frame costs microseconds; a narrated turn costs a model call of seconds on a single consumer GPU, and regenerating it does not reproduce the same words unless every call is cached and replayed. (2) Output permanence: a frame is overwritten before the eye settles; a paragraph has been read, remembered and acted on. GGPO's own guidance (defer effects until the rollback is done, expect short effects to vanish) has no equivalent for prose: there is no way to un-tell. (3) Rollback distance: fighting games roll back a handful of frames; the game's unit is a human turn, possibly days of game time, and other humans have built decisions on it (cascaded rollback through people). (4) Determinism: the engine side can be deterministic; the narrator is not part of the deterministic core.
- What survives. The split GGPO insists on (authoritative state separate from presentation; presentation is a pure function of state) is the same split as engine and narrator. Engine-only state that nobody has been told about can be rolled back or recomputed freely, so speculative pre-advance of regions and the lazy-cancellation admission test (section 2) are sound uses of rollback. The rule of thumb: rollback is available up to the first narration that depended on the state, never past it.
- The frame-delay knob is local lag again: the more delay a genre tolerates, the fewer rollbacks. A text game tolerates seconds, which is an argument for spending a little wait (hold the arrival scene briefly) rather than risking any retcon.

### Gaps
- No source was found on rollback in text or narrative multiplayer games; the limits above are reasoned from the stated requirements.
- The detailed body of the Infil article and other write-ups (frame counts typically rolled back) were not retrieved.

## 7. Multiversion and optimistic concurrency control: two players acting on the same person at different game times

### Takeaway
The proposal is multiversion timestamp ordering in which a too-early writer is given a later timestamp before it runs (so nothing aborts). Database theory supplies the soundness conditions: reads must be stamped as well as writes, range and absence reads need coarser protection (the region time), and per-object checks alone admit write skew.

### Cited Findings
- Snapshot isolation: a transaction gets a begin timestamp and reads the database as of that timestamp; at commit it gets a commit timestamp and succeeds only if no other transaction that committed in between wrote any item it wrote (first committer wins). It prevents read skew but allows write skew: two transactions each read something the other then writes, their write sets are disjoint, and both commit. It is stronger than read committed, incomparable with repeatable read, weaker than serialisable. — [Summary of Berenson, Bernstein, Gray, Melton, O'Neil, O'Neil, "A Critique of ANSI SQL Isolation Levels", SIGMOD 1995 (read)](https://mwhittaker.github.io/papers/html/berenson1995critique.html); [paper on arXiv](https://arxiv.org/abs/cs/0701157)
- Multiversion mechanisms keep successive versions of each item and can answer a read stamped earlier than the current version from an older one; faced with a write stamped earlier than the current version, they usually must abort the transaction and restart it with a later timestamp, which under contention wastes work and can starve. Time Warp applied to databases never aborts whole transactions; it rolls back only the causally affected part. With virtual time, transactions appear to commit strictly in timestamp order, a stronger condition than serialisability. — [Jefferson 1985, section 5.2 and related work (read)](https://gdo-pdes-course-2014.llnl.gov/attachments/20776356/20907222.pdf)
- In Reed's pseudotime scheme, actions at different pseudotimes may commit in either order, and an action with the earlier pseudotime may have to be aborted and retried later with a later one. — [Jefferson 1985, related work (read)](https://gdo-pdes-course-2014.llnl.gov/attachments/20776356/20907222.pdf)
- For interactive virtual environments, database-style locking and serialisation have been judged too slow to respond; alternatives are optimistic (proceed, roll back on conflict) or pessimistic (check first). Roberts and Sharkey's scheme passes an ownership key for an object and predicts who will need it next so that the key is requested before the interaction; Lee et al. limit the candidates to those within an area of interest around the current holder. — [Delaney et al. 2006 (read)](https://perso.lisn.upsaclay.fr/mbl/ENS/CSCW/2022/papers/Delaney2006.pdf)

### Inferences
- Reading the proposal as a database. A player action is a transaction with timestamp = the character's clock. Perceive = snapshot read at that timestamp from versioned world state. Touch = on a write to an item whose stamp is later than the transaction's timestamp, restart the transaction at the later timestamp; because the check happens before execution, "restart" costs nothing but the character's time. The result commits in timestamp order, which per Jefferson is stronger than serialisable. The irrevocable-output problem is the reason the game cannot use first-committer-wins as databases do (the loser has to abort, but here the first committer has already been narrated and the second has not yet run, so the second is the one that moves; the outcome is the same as first committer wins, with promotion instead of abort).
- "Two players act on the same person at different game times", worked through. Leader B (day 3) talks to the innkeeper: innkeeper's stamp becomes day 3 (and the conversation is narrated). Slower A (day 1) then talks to the innkeeper. Options the theory allows: (a) promotion: A becomes day 3, the innkeeper remembers B (what the proposal does); player A experiences a two-day skip. (b) Multiversion read only: A may observe the innkeeper as of day 1 but not change anything the day-3 conversation depended on; in practice a conversation always writes (memory, attitude), so this is only viable for looking, not talking. (c) Validation: let A's day-1 conversation run in the engine, then check whether any fact given to B's narration would differ; if not, commit it at day 1 (the innkeeper "had also spoken with A two days earlier", unmentioned to B); if so, fall back to (a). Option (c) is backward validation against narrations as committed readers; it is the least disruptive to A and the most work to build, and it is fragile exactly where narrations make broad claims.
- Write skew in the game. A (day 1) reads "the bridge stands" and sends a caravan across; B (day 2) reads "no caravan is due" and burns the bridge. No object is written by both, so no stamp fires, and in timestamp order nothing is wrong (the caravan left before the fire). The danger is the mirror case, where the slower player's later-submitted, earlier-dated write changes something the leader was told through a different object (B asked a guard on day 2 whether a caravan was due and was told no; A then dispatches one on day 1). Preventing this needs the leader's read to stamp what it read (the caravan schedule), or a coarse stamp over the whole region, or validation of A's write against B's narration read set. Per-object last-touched times on acted-upon things alone do not catch it.
- Phantoms. "Nobody is here", "nothing has changed", "no news" are predicate reads. Databases need range or predicate protection for these; the region time is the game's range lock. It should be advanced by narration of the region, not only by actions in it.
- Starvation has a game form. In databases a transaction that keeps being restarted starves. A slow player who keeps being promoted by faster players' stamps never gets to live their own days. The window bounds each jump but not the count; a fairness rule (for instance, the leader blocks rather than the follower skipping, once the follower has been skipped recently) is the analogue of starvation avoidance.
- Predictive ownership keys suggest a lighter alternative for hot objects: a character about to engage a shared person "holds" that person for the scene, others are told the person is busy (a diegetic lock), and the hold is released with the stamp. Pessimistic, simple, and often natural in fiction.

### Gaps
- Kung and Robinson, "On Optimistic Methods for Concurrency Control" (ACM TODS 6(2), 1981) was not retrieved. From background knowledge: transactions run in read, validation and write phases; validation checks the transaction's read set against the write sets of transactions that committed while it was running, and restarts it on overlap. The validation option above is modelled on this but is not cited to the primary source.
- Serializable snapshot isolation (Cahill et al. 2008), which detects write skew by tracking read-write dependencies, is the obvious next reference for option (c); not researched.

## 8. Published work on temporal models for persistent or asynchronous multiplayer narrative, multi-participant interactive drama, or subjective time in multi-user simulations

### Takeaway
Very little formal work addresses several humans at different story times in one persistent narrative world. The nearest are Benford and Giannachi's trajectories framework (story time versus clock time for shared interactive narratives, including synchronising participants), the delayed-consistency and perception-filter line in virtual environments, and tabletop practice (strict campaign calendars for several groups in one world). I found no published system that combines per-participant clocks with irrevocable generated narration.

### Cited Findings
- Benford and Giannachi, "Temporal trajectories in shared interactive narratives" (ACM CHI 2008): a framework that maps story time against clock time. Canonical trajectories are the author's intended mapping; participant trajectories are each person's actual path through both; historic trajectories are later selections from recorded participant paths used to build histories. The framework is used to discuss disengaging and re-engaging, synchronising participants, and travel across time. It grew out of a slow, text-message-based game (Blast Theory's Day of the Figurines), about which the same authors later published a five-layer account of time in networked narratives (Leonardo, 2009). — [University of Exeter repository record (abstract and search excerpts only; full text blocked)](https://ore.exeter.ac.uk/repository/handle/10871/16154?show=full)
- A recent paper proposes a system-level metric, narrative interaction coherence, for distributed immersive storytelling, scoring causal-order violations, timing misalignment between dependent events, and divergence of replicated state, with collaborative storytelling modelled as a causally constrained event graph. — [Dublin City University repository, "Preserving Narrative Integrity in Distributed Immersive Storytelling through Coherence Aware Adaptation" (search excerpt only)](https://doras.dcu.ie/32927/1/Preserving_Narrative_Integrity_in_Distributed_Immersive_Storytelling_through_Coherence_Aware_Adaptation.pdf)
- Porteous and colleagues (AAMAS 2011) give an explicit model of narrative time as a control mechanism for generated interactive stories; it is single-user. — [Porteous et al., AAMAS 2011 (search excerpt only)](https://cs.huji.ac.il/%7Ejeff/aamas11/papers/D3_G56.pdf)
- A 2026 preprint argues for one persistent world state linking narrative interpretation and gameplay, with earlier narrative facts kept available until later events change them. — [arXiv 2608.04037 (search excerpt only)](https://arxiv.org/pdf/2608.04037)
- Tabletop precedent: the first-edition Advanced Dungeons and Dragons Dungeon Masters Guide (1979) insists that a campaign is meaningless without strict time records. Early "grand campaigns" ran many groups in one world on one calendar tied to real time (a suggested ratio was one real week to one game month), which kept everyone on the same schedule and forced players to keep several characters because a recovering or training character was unavailable. The cost was the referee's time. A later edition dropped the idea, saying time passed in earlier adventures has little effect on the current session. — [DM David, "Dungeons & Dragons and the Dream of the Grand Campaign" (read; secondary source quoting the rulebook)](https://dmdavid.com/tag/dungeons-dragons-and-the-dream-of-the-grand-campaign/)
- In virtual-environment research, "users see the same consistent world at different times" is an established position (delayed consistency), and Sharkey et al. explicitly offer users a relativistic physics in which delays make sense. — [Delaney et al. 2006 (read)](https://perso.lisn.upsaclay.fr/mbl/ENS/CSCW/2022/papers/Delaney2006.pdf)
- HLA explicitly supports human-in-the-loop simulators as federates that are neither regulating nor constrained (training simulators exchanging receive-order messages), accepting temporal anomalies for responsiveness. — [Fujimoto, HLA slides (read)](https://sigsim.acm.org/conf/mskr/Courseware/Fujimoto/Slides/FujimotoSlides-21-HLATimeManagement.pdf)

### Inferences
- The trajectories vocabulary fits the game well and may be useful in design documents: each character has a participant trajectory (game time against real time); the proposal's rules are constraints on how far trajectories may separate (window) and on how they may cross (touch), and the logs of what the leader lived through are historic trajectories from which the slower player's dated perceptions are drawn (perceive).
- The grand-campaign solution is clock synchronisation to real time: it is the "physical clocks kept within a bound" answer, and it removes the problem by removing per-character clocks. Its known costs (waiting in real time, characters unavailable) are what the proposal is trying to avoid. The 1979 rule and the proposal sit at opposite ends of the same dial; the window rule is a partial move back toward the calendar.
- Because no published design combines per-participant clocks with irrevocable narration, the game's design should be argued from the simulation and database results above rather than from precedent in narrative research.

#### Cross-cutting synthesis (inference)
- One formula recurs under three names. Conservative lookahead (airport flight time), the distance-matrix optimisation, and the perception filter's speed-limited time contour all say: the permissible time difference between two participants is the minimum time for influence to travel between them. A fixed two-day window is a constant approximation to that function.
- Two, and only two, ways exist to make irrevocable output safe without rollback: wait until nothing earlier can arrive (block the leader; conservative grant; local lag), or stamp what the output depended on so that later arrivals are dated after it (move the follower; Lamport max; timestamp-ordering restart). The proposal uses the second everywhere and the first only at the window edge. Each has a human cost (waiting in real time; losing game time without asking), and neither can be engineered away, only bounded and distributed fairly.
- Soundness checklist that the theory adds to the proposal as stated: (1) narration must stamp what it read, not only what was acted on; (2) scene-level and absence claims need the region stamp, and remote absence claims should be avoided or hedged; (3) equal-timestamp events need a deterministic tie-break; (4) skipped intervals need elapsed-time effects and an account in the fiction; (5) idle players must leave the minimum, and re-enter at or above it; (6) with many players the window must be scoped by interest (who can reach whom), not global; (7) long actions should be interruptible requests, granted short when something reaches the character first; (8) keep unobserved, uninfluenced world processes as pure functions of time so that they need no stamps at all.
