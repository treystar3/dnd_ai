# shipping: The game as the player installs and runs it

This workstream makes the built game start, tells the player why when it cannot, and puts what it writes where the player is pointed. A game built from this tree fails its own startup check today (the check reads source files a build does not carry), and nothing builds or starts the package, so the suite stays green over it. The plan builds eight pieces of infrastructure: one reader of the code's source in the startup check (the helper STARTUP_DATA-1 also plans, built once) with a self-check the exe runs (`--check`), a CI job that builds, installs and starts the package, one helper that places beside the exe the files written today under the code's own folder, one way an end is told, one way of leaving, a checked fetch shared by the tools and the update, one sender for the page, and a file of the window's own numbers and lines. The counting of tests that skip and the browser job for the page tests are TESTS-7's (tests workstream): needed here, not built twice. No feature changes what the model is asked or moves a recording; the data hash moves only if the owner puts the window's file under data/rules (SHIPPING-4). The owner is left eight choices (where the window's numbers and lines live, a window closed in the middle of a turn, what proves who made an installer, the WebView2 bootstrapper, model files an older release left, how long a browser page may be gone, the built game's text version, the transcript's cap) and the reading of the new lines a player or tester would see (features 5, 8, 9, 11, 15 and 17). No built exe and no installer was run by the audit, by this plan or by its review; SHIPPING-1 and SHIPPING-2 are what make that happen.
