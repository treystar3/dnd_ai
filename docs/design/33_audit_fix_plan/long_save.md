# long_save: What grows or slows over a long campaign

This workstream makes the owner's rule "every store has a cap or a window, and every cost per turn stays flat as the save ages" (GOALS.md 119-120) something the suite holds, and then mends each store and each per-line cost the audit found breaking it. It builds four pieces of infrastructure: a registry in which every store (in the save, under logs and in the process) names what bounds it, with a census test that fails on one that does not; one forget step for a place that leaves the map; one route search per start, kept under the map's version; and narrow readers, so a plain line no longer parses the whole world fourteen times. Around those sit small single-place mends: the refused answer that pins its turn in memory, the captive names that run out, the memory trimmed first because it has no minute, and the logs, lists and rows with no cap. Running a check for this plan found one fault no finding names: a captive escorted through a road stop is removed with the stop's own people; LONG_SAVE-18 covers it, with a second case of the same kind its review found in the code (a companion let go at a stop is kept there and then removed with it). Left to the owner: whether standing lands at a road stop, how long each kind of final record and each kind of departed person is kept, how many lines of item history the journal keeps, whether ended arcs are capped now or with their move to situations, and whether the taken item names keep every name (so none is ever given twice) or a window. No feature adds or changes a rule in a prompt; one (LONG_SAVE-12) shortens a list a request carries, and is measured.

## Features
